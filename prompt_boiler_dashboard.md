# Задача: дашборд складов и бойлеров (agromir-boiler-server)

Ты работаешь в уже существующем репозитории `agromir-boiler-server` со следующей структурой:

```
agromir-boiler-server/
├── infra/
│   ├── nginx/default.conf
│   ├── .env
│   └── docker-compose.yml
└── services/
    ├── api/            # Go + Gin
    │   ├── cmd/
    │   ├── internal/
    │   ├── .env
    │   ├── Dockerfile 
    │   ├── go.mod
    │   └── go.sum
    └── frontend/        # React + Vite + TypeScript
        ├── src/
        ├── public/
        ├── package.json
        ├── vite.config.ts
        └── tsconfig*.json
```

`docker-compose.yml` уже поднимает `postgres` (БД `agromir_boiler`, пользователь `main`), `api` (порт 8002→8000) и `frontend` (порт 8080→80) через nginx. **Агента бойлера (сбор данных из WinCC) сейчас НЕ трогаем** — делаем только серверную часть: БД → API → фронт, с тестовыми (сид) данными. Интеграция с реальным агентом будет отдельным этапом позже.

Нужен полностью рабочий MVP, без ошибок компиляции/рантайма, который поднимается одной командой `docker compose up -d --build` и сразу показывает тестовые данные.

---

## 1. Бизнес-логика / предметная область

Завод хранит сырьё в ёмкостях (бойлерах), сгруппированных по складам:

- **Склад 1** — ёмкости №1–8
- **Склад 2** — ёмкости №9–16
- **Склад 3** — ёмкости №17–24

Для каждой ёмкости в каждый момент времени известны:

| Параметр | Описание |
|---|---|
| `level_mm` | Уровень налива H, мм |
| `density` | Плотность, т/м³ |
| `volume_m3` | Объём, м³ |
| `volume_l` | Объём, л |
| `mass_t` | Масса, Т |
| `income_month` | Приход за месяц |
| `outflow_month` | Расход за месяц |
| `income_year` | Приход за год |
| `outflow_year` | Расход за год |

Объём/масса в реальной системе считаются по градуировочной таблице (диаметр ёмкости 5300 мм, угол наклона днища 2°, шаг цилиндра ≈22.062 л/мм) — **в этом MVP формулу не реализуем**, просто храним и отдаём уже готовые числа (как они в будущем придут от агента).

Также нужен **почасовой тренд за последние сутки** (24 точки) по уровню/объёму/массе для графика.

## 2. Пользовательский сценарий (3 экрана)

### Экран 1 — Выбор склада
Три крупные кнопки: **Склад 1**, **Склад 2**, **Склад 3**. Под каждой кнопкой — суммарный объём склада (м³), подтягивается с бэка, не хардкод.

### Экран 2 — Выбор ёмкости
После выбора склада — сетка кнопок с номерами ёмкостей (для Склада 1 это кнопки 1–8, расположены 2 колонки × 4 строки, как на референсе: `1 2 / 3 4 / 5 6 / 7 8`). Кнопка с пустой ёмкостью (уровень 0) визуально приглушена (серая), но кликабельна. Сверху — кнопка "Назад" к выбору склада.

### Экран 3 — Карточка ёмкости
Сверху — переключатель из двух вкладок: **Информация** (активна по умолчанию) и **График**. Переключатель в виде двух кнопок/табов, подпись слева "Информация", справа кнопка "График" (как описано заказчиком).

**Вкладка "Информация"** — таблица/список:
```
Объём, м³:        159.94
Объём, л:         159 939.17
Масса в Т:        215.92
Приход за месяц:  1.35
Расход за месяц:  1.35
Приход за год:    1.35
Расход за год:    1.35
```
Плюс сверху текущий уровень налива (мм) и дата/время последнего обновления.

**Вкладка "График"** — заголовок "Тренд уровня, объёма, массы за сутки" и линейный график с тремя линиями (уровень / объём / масса) по часам за последние 24 часа. У каждой линии своя ось или нормализация — выбери сам наиболее читаемый вариант (можно 3 отдельных мини-графика друг под другом вместо одного с тремя осями — это даже предпочтительнее по читаемости).

### Глобальные элементы
- Справа сверху на всех экранах — **круглая кнопка переключения темы** (тёмная/светлая), иконка солнце/луна, тема сохраняется в `localStorage` и применяется мгновенно без перезагрузки.
- Хлебные крошки или кнопка "Назад" на экранах 2 и 3.
- Адаптивность: должно нормально выглядеть и на десктопе, и на планшете (это экран оператора на заводе, скорее всего широкий монитор или планшет).

## 3. Схема БД (PostgreSQL, добавить как SQL-миграцию в `services/api`)

```sql
CREATE TABLE warehouses (
    id          SERIAL PRIMARY KEY,
    name        TEXT NOT NULL,
    sort_order  INT NOT NULL
);

CREATE TABLE boilers (
    id            SERIAL PRIMARY KEY,
    warehouse_id  INT NOT NULL REFERENCES warehouses(id),
    number        INT NOT NULL UNIQUE,      -- сквозной номер 1..24
    position      INT NOT NULL,             -- позиция внутри склада 1..8
    diameter_mm   INT NOT NULL DEFAULT 5300,
    height_max_mm INT NOT NULL DEFAULT 7400
);

-- Текущий снэпшот по каждой ёмкости (последнее известное значение)
CREATE TABLE boiler_readings (
    boiler_id      INT PRIMARY KEY REFERENCES boilers(id),
    ts             TIMESTAMPTZ NOT NULL,
    level_mm       NUMERIC NOT NULL,
    density        NUMERIC NOT NULL,
    volume_m3      NUMERIC NOT NULL,
    volume_l       NUMERIC NOT NULL,
    mass_t         NUMERIC NOT NULL,
    income_month   NUMERIC NOT NULL DEFAULT 0,
    outflow_month  NUMERIC NOT NULL DEFAULT 0,
    income_year    NUMERIC NOT NULL DEFAULT 0,
    outflow_year   NUMERIC NOT NULL DEFAULT 0
);

-- Почасовая история за сутки (для графика), потом сюда же будет писать агент
CREATE TABLE boiler_trend (
    id         BIGSERIAL PRIMARY KEY,
    boiler_id  INT NOT NULL REFERENCES boilers(id),
    ts         TIMESTAMPTZ NOT NULL,
    level_mm   NUMERIC NOT NULL,
    volume_m3  NUMERIC NOT NULL,
    mass_t     NUMERIC NOT NULL,
    UNIQUE (boiler_id, ts)
);
CREATE INDEX idx_boiler_trend_boiler_ts ON boiler_trend (boiler_id, ts DESC);
```

Сделай это либо SQL-функцией с `generate_series`, либо Go-скриптом/seed-командой при старте, если так будет чище.

## 4. API (Go + Gin, `services/api`)

Базовый путь: `/api/v1`. Используй уже существующие `internal/` пакеты репозитория (handlers/services/repository слоями — посмотри текущую структуру `internal/` перед тем как добавлять файлы, и следуй тому же паттерну). Подключение к Postgres — через переменные из `.env` (уже есть `docker-compose.yml` с сервисом `postgres`).

### `GET /api/v1/warehouses`
```json
[
  { "id": 1, "name": "Склад 1", "total_volume_m3": 1179.84 },
  { "id": 2, "name": "Склад 2", "total_volume_m3": 318.82 },
  { "id": 3, "name": "Склад 3", "total_volume_m3": 0 }
]
```

### `GET /api/v1/warehouses/:id/boilers`
```json
[
  { "id": 1, "number": 1, "position": 1, "level_mm": 7298, "volume_m3": 159.94, "is_empty": false },
  { "id": 4, "number": 4, "position": 4, "level_mm": 2976, "volume_m3": 63.70, "is_empty": false }
]
```

### `GET /api/v1/boilers/:id`
Текущий снэпшот (всё из `boiler_readings` + номер/склад), поля ровно как в таблице "Информация" из п.2.

### `GET /api/v1/boilers/:id/trend`
```json
{
  "boiler_id": 1,
  "points": [
    { "ts": "2026-10-12T15:00:00Z", "level_mm": 7280, "volume_m3": 159.5, "mass_t": 215.3 },
    { "ts": "2026-10-12T16:00:00Z", "level_mm": 7291, "volume_m3": 159.7, "mass_t": 215.6 }
  ]
}
```

Все три эндпоинта — `GET`, без авторизации (внутренний дашборд за nginx, авторизацию добавим позже отдельным этапом). Обязательно CORS middleware, разрешающий фронт (в dev — `*`, или конкретный origin фронта). Обработка ошибок — единый JSON `{ "error": "..." }` с корректными HTTP-кодами (404 если склад/бойлер не найден, 500 с логированием на реальных ошибках БД).

## 5. Фронтенд (React + TypeScript + Vite, `services/frontend`)

### Структура компонентов
```
src/
├── api/
│   └── client.ts              # fetch/axios-обёртка, базовый URL из VITE_API_URL
├── theme/
│   ├── ThemeContext.tsx        # контекст + localStorage persist
│   └── theme.css               # CSS-переменные для light/dark
├── components/
│   ├── ThemeToggleButton.tsx   # круглая кнопка солнце/луна, фикс. сверху справа
│   ├── BackButton.tsx
│   ├── WarehouseCard.tsx
│   ├── BoilerButton.tsx
│   ├── BoilerInfoPanel.tsx
│   └── BoilerTrendChart.tsx    # recharts, 3 линии/3 мини-чарта
├── pages/
│   ├── WarehouseSelectPage.tsx # Экран 1
│   ├── BoilerGridPage.tsx      # Экран 2
│   └── BoilerDetailPage.tsx    # Экран 3, табы Информация/График
├── types.ts
├── App.tsx                     # роутер (react-router-dom)
└── main.tsx
```

### Технологии
- **react-router-dom** для переходов `/ → /warehouse/:id → /warehouse/:id/boiler/:boilerId`.
- **recharts** для графика (три `<LineChart>` друг под другом или `<ResponsiveContainer>` с несколькими `<Line>` — выбери вариант почитабельнее; добавь `recharts` в `package.json`).
- Переключение вкладок Информация/График — просто локальный `useState`, без роутинга смены URL (или с query-параметром `?tab=chart`, на твой выбор, но состояние должно сохраняться при обновлении страницы — если делаешь через state, это не критично для MVP).
- Тема — CSS-переменные (`--bg`, `--surface`, `--text`, `--accent` и т.д.) на `:root` и `[data-theme="dark"]`, переключение через атрибут `data-theme` на `<html>`, применяется без мигания при загрузке (читай `localStorage` синхронно до первого рендера).
- `.env` фронта: `VITE_API_URL=http://localhost:8002/api/v1` (или относительный `/api/v1`, если nginx проксирует — проверь `infra/nginx/default.conf` и используй то, что там уже настроено; если проксирования `/api` на `api:8000` там ещё нет — добавь).

### Дизайн
- Крупные, легко нажимаемые кнопки (это экран оператора, возможно touch-дисплей) — минимум 64px высотой для кнопок складов/ёмкостей.
- Чёткая иерархия: заголовок текущего склада/ёмкости всегда виден вверху.
- Пустые ёмкости (`is_empty: true`) — приглушённый цвет кнопки + небольшая подпись "пусто".
- Цифры объёма/массы — моноширинный или табличный шрифт для ровного выравнивания в карточке "Информация".
- Не используй чужие логотипы/бренд-цвета — нейтральная индустриальная палитра (графит/синий для тёмной темы, светло-серый/синий для светлой).

## 6. Критерии приёмки

1. `docker compose up -d --build` в `infra/` поднимает postgres+api+frontend без ошибок, миграции и сид применяются автоматически при первом старте (миграция запускается из кода API при старте приложения, либо отдельным init-контейнером/скриптом — выбери то, что проще встроить в текущий `Dockerfile` сервиса `api`).
2. Открыв фронт, пользователь видит 3 кнопки складов с подписанным суммарным объёмом.
3. Клик по складу → сетка ёмкостей (8 штук, 2×4), пустые визуально отличаются.
4. Клик по ёмкости → карточка с вкладкой "Информация" (все 7 полей из п.2, с текущими значениями из БД) и вкладкой "График" (рабочий, кликабельный переключатель — **это обязательно должно работать**, переключение между вкладками мгновенное, без перезагрузки страницы).
5. На вкладке "График" — реальные данные за 24 часа из `boiler_trend`, три видимых тренда (уровень/объём/масса), с подписанными осями и легендой.
6. Круглая кнопка темы в правом верхнем углу на всех экранах, переключает тёмную/светлую тему мгновенно, тема сохраняется между перезагрузками страницы.
7. Нет ошибок в консоли браузера, нет паник/500-х в логах `api`.
8. Код разложен по файлам согласно структуре выше, а не в одном файле — компоненты переиспользуемые, типы данных описаны в `types.ts`, запросы к API централизованы в `api/client.ts`.

## 7. Что сейчас НЕ делать

- Не трогать и не создавать агента для WinCC/локального SQL — это отдельный следующий этап.
- Не делать авторизацию/логин — добавим позже.
- Не реализовывать реальную формулу перевода уровня в объём по градуировочной таблице — просто хранить и отдавать уже готовые числа.
